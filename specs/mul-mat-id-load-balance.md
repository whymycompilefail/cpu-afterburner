# MUL_MAT_ID 负载切分：从静态行切片改成抢块

> 状态：**已实现并定版**（`MMID_DYNAMIC 1`）
> 基线：`5096f2a` + 本仓库 patch
> 适用：**MoE 模型**（dense 模型的 `MUL_MAT_ID` 调用数为 0，无影响）

---

## 0. 一句话

decode 阶段 MoE 的 `MUL_MAT_ID` 里，每个线程分到固定的一段专家×行，**分到小专家的线程早早就闲了**。
改成从线程池计数器上抢块之后，不均衡从 `max/mean 1.173` 降到 `1.030`，
decode **+5.7%**、prefill **+18.3%**（同批交替，4/4 轮单向）。

---

## 1. 怎么发现这是瓶颈的

先移植 profiler（见 `op-profiler.md`），在 gpt-oss-20b-MXFP4 / 单 token 52.3 ms 的图上看到：

| op | 占比 |
|---|---|
| `MUL_MAT_ID` | **46.4%** |
| `MUL_MAT:q8_0` | 44.6% |
| `ADD_ID` | 3.1% |

光看占比只能说明"这里花时间多"，不能说明"这里有浪费"。`GGML_OPPROF=2` 的逐节点 trace
给出每线程耗时后，浪费才显形：

```
MUL_MAT_ID  max/mean = 1.173      ← 最慢线程比平均多跑 17%
整图浪费              11.8%
```

`max/mean` 的含义：如果所有线程完全均衡，最慢的应该正好等于均值。1.173 说明
**关键路径上白白等了 17%**。

反过来验证机制：`result_output`（head，单节点 615 MB）的 `max/mean` 是 **1.002**。
同一个线程池、同一套切分机制，大 op 完全均衡 ⇒ **不是线程池坏了，是切分策略在小 op 上不适配**。

---

## 2. 为什么静态切分会失衡

`forward_mul_mat_id` 处理的是"一批 token，每个 token 路由到不同专家"。stock 的实现把
`(专家, 行)` 空间按 `(ith * ne01) / nth` 切成连续片段，一个线程一段。

问题在于每个专家分到的 token 数不服从均匀分布：Mixture-of-Experts 的路由本身就是不均衡的。
分到"只有 2 个 token 的专家"的线程，几微秒就干完了，然后站在屏障上等其他线程。
分到"40 个 token 的专家"的线程要跑到底。

**这不是负载不均，是负载不可知**——静态切分在动手之前就决定了份额，而份额的真实成本只有跑起来才知道。

---

## 3. 实现

### 3.1 块网格

把整个 `(专家, 行)` 空间切成 `total_chunks` 个块，块边界**必须对齐 `NB_COLS = 8`**：

```c
// NB_COLS=8 的边界对齐不是可选项：不对齐时 gemv 会静默丢掉部分列组
// （不报错、不崩溃，结果就是慢一点 + 数值略有偏差，极难发现）
```

对齐后记前缀和 `chunk_prefix[a]`（每个专家的块起点 + 总数），`ith == 0` 算完就把
`total_chunks` 交给线程池：

```c
ggml_threadpool_chunk_set(params->threadpool, nth);
```

### 3.2 抢块循环

```c
while (cur_chunk < total_chunks) {
    // 处理 cur_chunk 对应的 (专家, 行范围)
    cur_chunk = ggml_threadpool_chunk_add(params->threadpool, 1);
}
```

关键点是**允许跨专家前进**：一个线程干完专家 3 的块，可以接着抢专家 7 的块，
不需要跟任何人同步。这让"快线程多干、慢线程少干"自然发生，而不需要事先估计成本。

### 3.3 🔴 必须是编译期开关

```c
#define MMID_DYNAMIC 1
#define MMID_DYNAMIC_CHUNKS 4
```

**不能做成运行期开关**，代价实测如下：

> 把同一段 stock 循环**原样**包进一个运行期 `if`，else 分支为空，
> 别的什么都不改：**19.26 → 14.32 tok/s（−26%）**。

`gemv<>` 是巨型模板，MSVC 一旦见它落在分支内，就不再生成原来那份代码。症状极具有误导性——
diff 看起来"只是加了个 if"，性能却掉四分之一，会让人以为是新逻辑有问题。

所以两个变体是**两份独立构建**，在这里用宏选。

## 4. 实测

### 4.1 均衡度（profiler，同批）

| | stock | dynamic |
|---|---|---|
| `MUL_MAT_ID` max/mean | 1.173 | **1.030** |
| `MUL_MAT_ID` 浪费 | 3,761 μs | **666 μs** |
| 整图浪费 | 11.8% | **4.8%** |
| 关键路径 | 46,034 μs | **43,047 μs** |

### 4.2 llama-bench（同批交替，每轮 A/B 相邻）

| | stock | dynamic |
|---|---|---|
| tg128 @t=14 | 18.82 | **19.90**（+5.7%，4/4 轮） |
| pp512 @t=14 | 49.55 | **58.64**（+18.3%，4/4 轮） |

### 4.3 交付形态（各自最优线程数）

| | stock@16 | dynamic@18 |
|---|---|---|
| tg128 | 20.04 / 20.14 / 19.80 | **21.60 / 21.42 / 21.75**（+8.0%） |
| pp512 | 52.4 ~ 53.5 | **64.7 ~ 65.3**（+22.9%） |

线程数最优点从 14 上移到 **18**（峰 21.5）。这跟 stock 下"t=22 掉 17%"的形状不同：
抢块之后多出来的线程有活可抢，SMT 兄弟争抢的惩罚被摊薄了。

### 4.4 粒度无关

`MMID_DYNAMIC_CHUNKS = 2 / 4 / 8` 三档全部落在噪声内。

⇒ **收益来自"跨专家领活"，不是"切得更细"**。这条很重要：它意味着不需要调这个参数，
也意味着继续往下切不会有更多收益。

---

## 5. 端到端与一个必须说清的界限

54 题代码修复池（本地 2B 模型 + 云端升级）：**墙钟 683 s → 638 s（−6.6%，45/54 更快）**。

但同一个批次的**真实请求 decode 是 18.46 → 18.34，持平**。

原因不神秘：真实请求带长上下文，每个 step 要读的 KV cache 把 decode 收益摊平了；
而 prefill 那部分收益是实打实的。所以准确的说法是：

> **我们拿到的是一笔 prefill 收益，不是 decode 收益。**

短上下文 bench（tg128）的 +5.7% 是真的，但它不等于"日常生成快 5.7%"。
三个数——bench、真实请求 decode、端到端墙钟——不是一回事，不能互相替代。

## 6. 被推翻的结论（如果看到旧笔记，按这里为准）

| 旧结论 | 现状 |
|---|---|
| "动态切分比静态慢 5%" | **作废**。那是运行期 `if` 包装的产物（−26%），不是动态切分本身 |
| "切得越细越好" | **作废**。2/4/8 在噪声内，收益来源是跨专家领活 |
| "decode 13.x tok/s" | **作废**。绝对值受跨批次漂移影响（约 5%），只认同批交替的比值 |
| "带宽 41.8 GB/s 是上限" | **作废**。那是 Qwen 模型测的；head 单 op 实测 **62~66 GB/s** |
| "慢核应该避开" | **作废**。只用 12 个快核（t=12）是最差配置，比 t=18 低 13%——慢核照样贡献带宽 |

## 7. 复现

```bash
bash scripts/setup.sh                       # 会编出 llama-bench
cd llama.cpp

# 同批交替 A/B：两次构建各编一遍，交替跑，只比比值
#   MMID_DYNAMIC 0 编一次 -> bin_stock
#   MMID_DYNAMIC 1 编一次 -> bin_dyn
./bin_dyn/llama-bench   -m <moe.gguf> -p 512 -n 128 -t 18 -fa 1 -r 2
./bin_stock/llama-bench -m <moe.gguf> -p 512 -n 128 -t 16 -fa 1 -r 2

# 看不均衡（退出时打表）
GGML_OPPROF=2 ./bin_dyn/llama-bench -m <moe.gguf> -p 0 -n 1 -t 18 2>&1 | tail -40
```

⚠️ 跨批次绝对 tok/s 漂移约 5%（升频 / 页热身 / 温度）。**顺序扫描还会骗人**：
从 t=12 一路测到 t=22，会造成"越测越快"的假象，把最后那个伪装成最优。必须正反交替。
