# 踩过的坑

按"会不会让人做出错误决定"排序。前三条都会让一个本来对的改动看起来像错的。

---

## 1. 🔴 把热循环包进运行期 `if`，掉 26%

**症状**：把同一段 stock 循环**原样**包进 `if (cond) { ...原代码... }`，else 分支为空，
其余一字未改，性能从 **19.26 掉到 14.32 tok/s**。

**为什么**：`gemv<>` 是巨型模板。MSVC 一旦见它落在分支内，就不再生成原来那份代码，
即使 `cond` 是常量、即使分支永远为真。diff 看起来"只是加了个 if"，
性能却掉四分之一，会让人以为新逻辑有问题，然后去 debug 一个不存在的 bug。

**做法**：策略开关一律用 `#define`，编译期决定。

```c
#define MMID_DYNAMIC 1        // 不是 env，不是 if，不是命令行参数
```

发现过程值得记：V1 三个小改一起上 = stock 19.12（正常）；V2 只加一个空分支包装 = 14.32。
二分到这一步才敢确认是代码生成的问题。

## 2. 🔴 `git apply` 在仓库子目录里静默跳过，还返回 0

**症状**：

```
$ cd /d/Ai_edge_deployment/tmp/clean5096
$ git apply --check patches/xxx.patch
Skipped patch 'src/llama-graph.cpp'.
...
$ echo $?
0
```

**假的通过。** `git apply` 在子目录里会把**外层仓库的根**当作基准，
于是它认为 patch 里的路径（`src/llama-graph.cpp`）在仓库根下不存在，就跳过——
不是报错，是跳过，并且 exit code 0。

**验证 patch 时，快照必须放在任何 git 仓库之外。**
真正的链条是三步，缺一步都不算验过：

1. 确认基线迁移是纯 rename：`git diff --summary -M A B` 只有 rename 行
2. 干净快照上 `git apply --check` **逐个文件**通过（看输出里每个 `Checking patch ...`）
3. 真的编一遍，产物能跑

## 3. 🔴 `.patch` 文件被 CRLF 废掉

**症状**：`git add` 时警告 `LF will be replaced by CRLF`，之后 `git apply` 必败。

**为什么**：patch 的上下文行一旦带上 `\r`，就跟源文件对不上了。
而这个损坏发生在**提交时**，本地看文件是好的。

**做法**：`.gitattributes` 必须写

```
* text=auto eol=lf
*.patch -text
*.diff  -text
```

**验证要看到字节级**：从远端把 patch 取回来，跟本地 `cmp` 逐字节比，
并且 `grep -c $'\r'` 必须是 0。只看"文件大小差不多"不够。

---

## 4. Windows 批处理必须 ASCII + CRLF

用 UTF-8 中文注释 + LF 行尾写 `.bat`，`cmd` 会把 `rem` 行当命令执行；
路径里反斜杠混正斜杠（`%SDK%\Include/10.0...`）会触发 CMake 的
`Invalid escape '\P'`。

**做法**：`open(path, 'w', encoding='ascii', newline='\r\n')`。
中文注释写在 bash 脚本或 README 里，别写在 bat 里。

## 5. MSVC 的 `INCLUDE` 为空，报错指向源码

```
ggml.h(211): fatal error C1083: 无法打开包括文件: "stdbool.h"
```

看起来像源码缺头文件。实际是当前 shell 不是 MSVC 环境，`INCLUDE` / `LIB` 没设。
在「x64 Native Tools Command Prompt」里跑，或先 `call vcvars64.bat`。

**别去改源码**。这个坑会吃掉半小时，而且改错了还能编过（因为手动加了 `#include`），
留下一个污染。

## 6. 顺序扫描线程数会骗人

从 `t=12` 一路测到 `t=22`，tg 从 21.19 一路爬到 24.01，看起来"线程越多越快"。
第二圈整体又比第一圈高 15%。

**原因**：升频 / 页热身，机器越跑越快。最后测的那个被伪装成最优。

**做法**：正反交替（`12 14 … 22 / 22 20 … 12`），跑 4 轮取均值。
alternating 之后峰值才露出来：t=18（25.76），t=22 掉到 23.91。

顺带一个反直觉的：**t=14 是最不稳的点**（四轮里出现过 22.15，掉 8%），
大概率是这一档会让 SMT 兄弟同核。别拿单次测量下结论。

## 7. 别猜逻辑编号到物理核的映射

用 `-C 0xFF555 --cpu-strict 1` 想"只跑前 10 个物理核"，结果 13.9 → 7.0，腰斩。

**原因**：这台机器的逻辑编号不是"先排完所有物理核再排兄弟"，
`0-5` 和 `6-11` 是同一批物理核的 SMT 兄弟。按直觉选的掩码实际是在同一批核上塞两个线程。

**做法**：要绑核就先实测映射（`Win32_PerfFormattedData_Counters_ProcessorInformation`
能给每个逻辑处理器的性能数据）。没实测就别绑。

而且更根本的一点：**"避开慢核"这个思路本身是错的**。只用 12 个快核（t=12）
是最差配置，比 t=18 低 13%——慢核也贡献带宽，少线程的损失大于核间差异。

## 8. profiler：fusion 会推进 `node_n`，统计记错 op

`ggml_graph_compute_thread` 的循环里，fusion 会改变 `node_n`。
如果直接用循环推进后的下标做统计，时间会被记到邻居 op 上。

症状隐蔽：表能打出来、总时间也对，但某些 op 的时间错位，
于是你会去优化一个根本不热的算子。

**做法**：循环开头存下原始下标（`prof_n`），trace 汇总用它。

---

## 9. 改错了路径：`MUL_MAT_ID calls: generic=0 repack=648`

想优化 `MUL_MAT_ID`，第一反应是改 `ggml-cpu.c` 里的通用实现。
分派计数器显示 `generic=0 repack=648`——**实际跑的是 repack 路径**，
改通用实现等于白干。

所以那个计数器不是调试残留，它是**导航**。加它花了两行，省掉的可能是一次完整的错误方向。

---

## 10. 块边界必须对齐 `NB_COLS = 8`

动态切分的块边界不对齐 `NB_COLS` 时，`gemv` 会**静默丢掉部分列组**：
不报错、不崩溃，只是结果略偏、速度略慢。极难发现。

对齐一行代码，不写就要花一整天。

---

## 11. `temp=0` 不是逐位可复现

同一个提示词、同一个模型、同一个 temp=0，两次跑有 1 题翻面（39 vs 38）。
批处理里也见过单题随机翻转（`rotate` 那道，prompt 逐字相同）。

**做法**：单题差异不当结论。要主张差异，必须两次独立运行都同向。

（这也是为什么本仓库里所有性能数据都用"同批交替 A/B"——把不可控的抖动尽量配平。）
