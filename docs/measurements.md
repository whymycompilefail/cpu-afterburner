# 测量数据汇总

> ⚠️ 这里的数字来自**不同模型**（gpt-oss-20b-MXFP4 / Qwen3.5-2B Q4_K_M 等）、
> **不同批次**。跨行比较是无效的。每张表内部才可比。

---

## 0. 测量纪律（先看这条，否则下面的数都会用错）

1. **跨批次绝对 tok/s 会漂约 5%**（升频 / 页热身 / 温度）。
   **只有同批交替的比值可信**。
2. **顺序扫描会骗人**。从 t=12 测到 t=22 会看到"越测越快"，
   把最后那个伪装成最优。必须正反交替。
3. **三个不同的"提速"数**：短上下文 bench（tg128）、真实请求 decode、端到端墙钟。
   长上下文请求的 KV 读取会把 decode 收益摊平。
4. **一次只跑一个 server**。两个进程抢核，测出来的都是垃圾。
5. **`temp=0` 不是逐位可复现**。单题差异不当结论。

## 1. 实得带宽分层（decode 稳态）

这一组推翻了"带宽受限"这个前提。

| 对象 | B/elem | 实得带宽 |
|---|---|---|
| head 单 op（615 MB，q8_0） | — | **66 GB/s** |
| f16 | 2.000 | 41.8 GB/s |
| q8_0 | 1.062 | 35.3 GB/s |
| q4_k_m | 0.562 | 24.4 GB/s |
| q3_k_l | 0.430 | 24.1 GB/s |

**读法**：如果真是带宽受限，B/elem 越小、每次搬运越快，实得带宽应该**恒定或更高**。
实际上它随压缩率**下降**。⇒ 瓶颈是**每元素的解包指令成本**，不是内存。

head 那个 66 GB/s 是另一个参照点：它没有解包（q8_0 直接 int8 dot），
所以能跑到硬件的真实上限。14 个线程逐线程耗时差 **0.4%**（9334 vs 9314 μs），
说明线程池与切分都已饱和，没有可回收的余量。

全模型层面（gpt-oss-20b）：
- MXFP4（top4/32 激活）：~49 GB/s
- Q4_K_M：40 GB/s

## 2. 线程数曲线

### 2.1 小模型：`mcp2b_v4` 2B Q4_K_M（四轮正反交替）

| t | tg tok/s | pp tok/s |
|---|---|---|
| 12 | 22.38 | 131.4 |
| 14 | 23.66（**最不稳**，四轮中曾掉到 22.15） | 139.5 |
| 16 | 24.95 | 148.7 |
| **18** | **25.76**（峰，四轮 25.83/25.77/25.61/25.84，σ=0.11） | 150.0 |
| 20 | 25.04 | 150.4 |
| 22 | 23.91 | 149.4 |

16 → 18 是 +3.2%；18 → 22 掉 7.2%。

### 2.2 大模型：gpt-oss-20b-MXFP4（shipping 版，抢块已开）

| t | 相对表现 |
|---|---|
| 14 | 19.9 |
| **18** | **21.5（峰）** |
| 22 | 20.1（stock 下这一档掉 17%） |

**抢块之后最优点从 14 上移到 18**：多出来的线程有活可抢，
SMT 兄弟争抢的惩罚被摊薄。这是"负载均衡改变最优配置"的一个实例。

## 3. 核间差异（这台机器的永久事实）

同节点内把每线程耗时按 `us / mean` 归一化，再按逻辑 CPU 聚合：

| 逻辑 CPU | 相对耗时 |
|---|---|
| **2 ~ 9** | **1.07 ~ 1.11**（系统性慢 8~10%，稳定） |
| 其余 | 0.90 ~ 0.99 |

标准差 ±0.07。

**但不要据此"避开慢核"**：只用快核（t=12）是最差配置，比 t=18 低 13%。
慢核照样贡献内存带宽。

⚠️ 也别猜编号映射。这台机器上 `0-5` 与 `6-11` 是 SMT 兄弟，
不是"先 6 个物理核再 6 个兄弟"。

## 4. MUL_MAT_ID 负载均衡

| | stock | dynamic |
|---|---|---|
| `max/mean` | 1.173 | **1.030** |
| 该 op 浪费 | 3,761 μs | **666 μs** |
| 整图浪费 | 11.8% | **4.8%** |
| 关键路径 | 46,034 μs | **43,047 μs** |

对照组：`result_output`（head，615 MB 单节点）的 `max/mean` = **1.002**。
同一个线程池、同一套机制 ⇒ **失衡来自切分策略，不是线程池**。

粒度 `CHUNKS = 2 / 4 / 8`：三档全部落在噪声内。
⇒ 收益来自**跨专家领活**，不是切得细。

## 6. 端到端（54 题批处理）

| | 改动前 | 改动后 |
|---|---|---|
| 墙钟 | 683 s | **638 s（−6.6%，45/54 题更快）** |
| 真实请求 decode | 18.46 tok/s | 18.34 tok/s（**持平**） |
| 通过数 | 54/54 | 54/54 |

**这行"持平"是整张表里最重要的一行。** 它说明墙钟收益来自 prefill，
不来自 decode——凭 tg128 的 +5.7% 去预期"日常生成快 6%"会失望。

## 7. 被放弃的方向（测过，不划算）

| 方向 | 实测 | 判断 |
|---|---|---|
| head 重编码为 Q4_0 | 22 线程 +1.2%（噪声内）、16 线程 +5.1%/+6.4% | 省字节被解包指令吃回，上限约 +10%，不做 |
| 词表裁剪（裁 head 行） | 加载时 `check_tensor_dims` 硬失败 | 必须配 C++ 侧 `output_ids` 支持，未做 |
| `MUL_MAT` 也上抢块 | 天花板仅整图 2.2% | 要动 `gemv<>` 模板结构，而这条模板有"运行期 if 掉 26%"的记录。风险不对等，不做 |
| 更细的 `MUL_MAT_ID` 粒度 | 2/4/8 噪声内 | 收益来源不是粒度 |
| 只用快核 | t=12 比 t=18 低 13% | 方向错误 |

`MUL_MAT` 剩余失衡（1.15~1.20，约 1,321 μs）已查清归因：
- 换成 p90 后只剩 936 μs（385 μs 是单次离群，不可预测）
- 剩下的对应"8 个逻辑核位慢 8~10%"这个硬件事实
- 而 `Qcur` / `o_proj` 已经跑到 66~70 GB/s，慢的不是算法

⇒ **这不是可回收的浪费，是硬件位置。**
